### 센서 입력 10fps 원인 — 조명 시험과 저조도 AE 설정 조사 (2026-11-10, 보드 변경 없음)

**정정**: 이전 기록의 "밝기(YAVG)가 같으니 조명 변화가 아니다"는 틀린 판단. AE는 밝기를 일정하게 맞추도록 노출·게인을 조절하므로, 밝기가 같고 노출이 최대에 가까우면 오히려 어두운 환경이라는 신호임. 조명 판단은 노출·게인으로 해야 함

**조명 시험** (10초 간격 기록. 센서 값은 I2C로 레지스터를 직접 읽음: VMAX 0x3024, SHR0 0x3050, GAIN 0x3090, HMAX 0x3028. V4L2 컨트롤 값도 함께 기록하며 둘이 항상 같았음. 시각은 보드 UTC)

| 구간 | CIF 입력 | VMAX | SHR0 → 노출 | 게인 레지스터 | ISP 메인 간격 |
| --- | --- | --- | --- | --- | --- |
| 조명 켜기 전 (10:59~11:42, 약 43분) | 10fps (100ms) | 2250 | 26 → 2224라인 (상한) | 56 | 100ms |
| 조명 켠 직후 (11:42:52~11:43:13) | 10fps | 2250 | 26 → 2224라인 | 56 → 52 → 23 → 17 | 100ms |
| 켠 뒤 1~4분 (11:43~11:46:37) | 10fps | 2250 | 26 → 2224라인 | 8~21 | 100ms |

- 조명을 켜자 게인이 56에서 8~13으로 크게 떨어짐(밝아진 것은 확실). 그러나 **노출은 계속 상한(VMAX−26)이고 CIF 입력도 계속 10fps** → 입력 fps는 20으로 돌아오지 않음
- 센서 레지스터는 20fps 설정 그대로: VMAX 2250, HMAX 0x0672(1650). HMAX 1650은 0번 모드 레지스터 테이블 `imx415_linear_10bit_3864x2192_594M_regs`의 값 (`imx415.c` 684-718, 690, 모드 정의 1277). **노출 2224라인은 프레임 길이 2250라인 안에 있으므로 "노출이 프레임 간격을 넘어 10fps가 된다"는 가설과 레지스터 값이 맞지 않음**
- 이번 부팅(10:44 UTC)의 CIF 누적 프레임 37709 ÷ 경과 약 3780초 = 9.98fps → 부팅 직후부터 계속 10fps. 반면 이전 부팅들(1-b, 2번째 재부팅 등)에서는 같은 설정으로 CIF가 15~20fps였음 → **입력 fps가 부팅마다 달라지는 것으로 보임** (원인 미확인)
- 센서 클럭: CIF `sclk_m0_cif` 24 MHz (드라이버 모드 정의는 `IMX415_XVCLK_FREQ_37M`). 이 차이가 의미 있는지는 미확인

**저조도 AE 설정** (보드 `/oem/usr/share/iqfiles/imx415_CMK-OT2022-PX1_IR0147-36IRC-8M-F20.json`, SDK `media/out/isp_iqfiles`와 md5 동일 c541e72e…)

| `ae_calib/LinearAeCtrl/Route` | `TimeDot [0, 0.05, 0.05, 0.05, 0.1, 0.1]`, `GainDot [1, 1, 8, 256, 256, 1024]` | 노출을 0.05초까지 올린 뒤 게인을 256까지 올리고, 그다음에 노출을 0.1초(10fps 상당)까지 늘리는 경로 |

- 저조도에서 fps를 고정하는 방법 (적용 안 함): ① 지금처럼 rkipc가 `isFpsFix = true`로 고정(이미 적용 중) ② IQ json의 `AecFrameRateMode`를 `isFpsFix: 1, FpsValue: 20`으로 변경 ③ `Route.TimeDot` 최대값을 0.05로 낮춰 노출이 1/20초를 넘지 못하게 함 ④ `CISMinFps`를 20으로 변경. ②~④는 `/oem`의 IQ 파일 수정이 필요하고 저조도 화질(노이즈·밝기)에 영향
- 다만 위 측정에서는 AE가 이미 20fps 타이밍(VMAX 2250)을 지키고 노출도 프레임 안에 있으므로, 지금의 10fps 입력은 AE 노출 설정만으로는 설명되지 않음

### 센서 입력 클럭 가설 확인과 2-B (2026-11-10, 보드 설정 변경 없음)

**클럭 경로 (보드 DT·clk_summary, 드라이버 소스)**
- DT `i2c@ff470000/imx415@37`: `clocks = <0x41>`, `clock-names = "xvclk"`, `assigned-clock-rates` 없음, `pinctrl-0 = cam-io-1`(GPIO3 C5를 GPIO로, MCLK 출력 핀 아님), `reset-gpios`
- phandle 0x41 = `/out-osc-imx415`: **`fixed-clock`, `clock-frequency` 37,125,000 Hz**, `#clock-cells = 0` → 카메라 모듈 쪽 고정 발진기로 선언됨
- clk_summary: `out-osc-imx415` 37,125,000 Hz (enable 1, 트리 최상위). 24 MHz는 SoC `xin24m` → `mclk_ref_mipi0/1`(enable 0, 미사용). CIF proc의 `sclk_m0_cif:24000000`은 이 미사용 MCLK를 표시한 것으로 판단. debugfs는 조회마다 마운트 후 바로 umount
- 드라이버: 모든 4레인 모드가 `xvclk = IMX415_XVCLK_FREQ_37M`(37,125,000) 기대 (`imx415.c` 77, 1282 등). 전원 켤 때 `clk_set_rate(xvclk, cur_mode->xvclk)` 후 `clk_get_rate`가 다르면 `xvclk mismatched` 경고 (2675-2679) → 부팅 로그에 경고 없음
- 24 MHz가 들어갔다고 가정한 이론 fps: 드라이버는 fps를 INCK로 계산하지 않음(`max_fps` 고정, pixel_rate는 링크 주파수 기준). 센서 프레임 시간은 INCK에 반비례하므로 20 × 24 / 37.125 ≈ **12.9 fps**로, 관측된 10 fps와도 맞지 않음
- 참고: `/proc/rkcif-mipi-lvds`의 `fps:` 값은 `rate:`와 어긋나는 경우가 있어(예: `fps:15`인데 `rate:33ms`) 신뢰하지 않음. 실제 입력 fps는 CIF 누적 프레임(`frame amount`) ÷ 경과 시간으로 계산

- 확인(재부팅 2회 모두): `date`는 KST, `date -u`는 UTC, `hwclock`은 UTC 그대로. **OSD 시각이 한국 시간**: 재부팅 2의 캡처 프레임 OSD `13:24:26`, 같은 시각 VM의 `date`는 13:24:25 KST (재부팅 1도 OSD 13:13:45 / VM 13:13:44)
- 영향(확실): `heartbeat.c`는 시각 함수를 쓰지 않아 서버로 가는 값은 변함 없음. `[network.ntp] enable`은 두 ini 모두 0이라 rkipc의 +8시간 보정(`common/network/ntp.c` 210행)은 꺼져 있음. 이것이 켜지면 TZ와 겹쳐 틀어지므로 그대로 0 유지. `/etc/init.d/S99rtcinit`이 RTC가 1969년일 때 쓰는 `date -s 2024-01-01`은 이제 KST로 해석됨(해당 상황에서만, UTC로 9시간 어긋남)
- 보드 `ls -l`의 시각 표시도 KST로 바뀌어 보임(파일 자체 시각은 그대로)

### 입력 10fps 하락 조사 — 시계 점프 가설 (2026-11-11, 보드 설정 변경 없음, 재부팅 4회)

가설(사용자): 부팅 약 60초에 NTP가 시계를 2021년에서 2026년으로 점프시키는 순간 시각 기반 프레임레이트 제어가 꼬여 입력이 10fps로 떨어진다. rkipc 시작 뒤에 점프하면 하락, 시작 전에 점프하면 정상

**1. 시계를 맞추는 주체와 시점 (확실, 부팅 스크립트·로그 조회)**
- **RTC가 있고 유지됨**: 보드에 `rockchip-rtc`(ff1c0000.rtc)가 있어 커널이 부팅 **0.29초**에 시스템 시계를 RTC 값으로 설정(`setting system clock to 2026-11-11T04:42:55 UTC` 등, 4회 모두). 그래서 이번 재부팅에서는 부팅 처음부터 시계가 2026년이고, 2021년이 아님
- `S49ntp`: `ntpd -g`(서버는 pool.ntp.org). 시작 업타임 약 2.9초. 4회 모두 로그에 시각 조정·동기 기록 0건, `TIME_ERROR: Clock Unsynchronized`만 있음 → **ntpd가 시계를 바꾸지 않음**. 서버 응답은 `Unexpected origin timestamp ... does not match aorg`로 거절되는 줄만 보임(원인은 확인 안 함)
- rkipc의 NTP(`common/network/ntp.c`, +28800초 하드코딩)는 두 ini 모두 `[network.ntp] enable = 0`이라 꺼져 있음
- `S99rtcinit`: RTC가 1969년일 때만 `date -s 2024-01-01` 후 `hwclock -w`. 이번엔 해당 없음 (RTC가 1969년이었던 적이 있는 **콜드 부팅**에서만 일어날 수 있고, 그 값도 2021년이 아니라 2024년)
- rkipc 시작: 부팅 후 약 10초(4회 9.99~10.26초, `/proc/pid/stat`). heartbeat 약 6초

**2. 재부팅 4회, 업타임 12~173초를 1초 간격으로 기록 (확실)**

**3. 소스·바이너리 조회 — 시스템 시각(CLOCK_REALTIME)을 쓰는가**
- 라이브러리 **소스는 없음**: `media/isp/…/librkaiq`는 헤더와 데모(`rkisp_demo`)만 있는 prebuilt `.so/.a`, `media/rockit`은 예제·헤더와 prebuilt `librockit`. 그래서 디스어셈블(`readelf`, `objdump`)로 시각 함수 호출만 확인함
- **rkipc 소스**(확실): 프레임레이트 제어 경로에는 시각 함수가 없음. fps는 ini 값을 `rk_isp_set_frame_rate`와 VI `stFrameRate`로 정적 설정. `rkipc_get_curren_time_ms`는 `CLOCK_MONOTONIC`, `rk_signal_wait`만 `CLOCK_REALTIME`(세마포어 타임아웃). 벽시계는 OSD(`osd.c`의 `time`+`localtime`), JPEG 파일명, 저장 모듈, 꺼져 있는 NTP에만 쓰임
- **커널 드라이버**(확실): `rkcif`, `rkisp`, `imx415` 소스에 `ktime_get_real*`, `gettimeofday` 계열 호출 없음. 프레임 시각은 `ktime_get_ns()`(단조)
- **librockit**(디스어셈블, 심볼이 없어 함수 이름은 추정): 시각 도우미 2종 — `CLOCK_MONOTONIC`(id 1) 호출 지점 34곳+, `CLOCK_REALTIME`(id 0) 호출 지점 2곳(둘 다 로그 타임스탬프 출력으로 보임, 추정). 조건변수는 `pthread_condattr_setclock(…, 1)`로 단조 시계 사용. 문서도 `VIDEO_FRAME_INFO_S.u64PTS`는 `clock_gettime(CLOCK_MONOTONIC)`로 설정하라고 안내(MPI 가이드 6.9절)
- **librkaiq**: 보드에 올라간 `/oem/usr/lib/librkaiq.so`(md5 `12e07ebc…`, 1.68MB)는 SDK의 `media/out/lib/librkaiq.so`(md5 `4c4ebfed…`, 2.68MB)와 **다른 파일**. 둘 다 `AIQ v5.0x5.0`이고 보드 판은 심볼이 제거되어 함수 이름을 알 수 없음. SDK 판 기준으로 `gettimeofday` 호출 15곳, `pthread_cond_timedwait` 7곳(각각 직전에 `gettimeofday`로 절대 시각을 만드는 패턴)이고 `XCam::Cond::timedwait`, V4L2 버퍼 큐 `SafeList::pop`, `waitSignal`, `waitLastSensorDone`에 쓰임. 보드 판도 `timedwait` 3곳 모두 직전에 `gettimeofday`가 있음. **즉 rkaiq의 대기 시간은 시스템 시계 변경에 영향을 받을 수 있는 구조**(시계가 앞으로 점프하면 대기가 즉시 타임아웃)이며, 단조 시계 호출(id 1, id 4)도 있음. 다만 이는 점프가 **일어났을 때**의 이야기고, 아래처럼 이번에는 점프가 없었음

**4. 가설 판단**
- **이번 재부팅 4회에서는 가설이 성립하지 않음** (확실): ① 시계 점프가 4회 모두 없었음(RTC가 0.29초에 2026년으로 설정, ntpd는 조정 안 함). ② 점프가 없는데도 2회에서 10fps 하락이 일어났고(부팅 2, 4), 점프가 없는 나머지 2회는 정상이었음. 점프 유무로는 하락이 설명되지 않음
- **가설 자체를 완전히 기각한 것은 아님**(확인 필요): RTC가 초기화되는 **콜드 부팅(전원 제거 후 기동)**에서의 시계 점프는 이번 시험에 포함되지 않음. 그 경우에도 rkipc 시작(10초)보다 `S99rtcinit`이 늦고 ntpd도 조정하지 않으므로 이 보드에서 점프가 일어나는지부터 확인해야 함
- 그래서 해결 후보 "시계가 맞춰질 때까지 rkipc 시작 지연"은 **적용하지 않고 보류**(현재 데이터로는 효과 근거 없음)

**5. 이번 조사에서 새로 드러난 것 (확실한 관찰과 추측을 구분)**
- (확실) 하락한 두 부팅에서만 하락 시작 시각과 같은 순간(23.86초, 68.35초)에 커널 메시지 `rkcif-mipi-lvds: rkcif_check_buffer_update_pingpong …, state 2, curr_buf …, next_buf …`가 1번 찍혔고, 정상 부팅 2회에는 없었음. 이 메시지 앞뒤 ±6초의 다른 커널·syslog 이벤트(네트워크 설정, samba, wireguard 핸드셰이크 재시도)는 정상 부팅에도 같은 시점에 있어서 원인으로 보이지 않음
- (확실, 소스) 이 함수는 CIF 핑퐁 모드에서 **버퍼가 모자라(`lack_buf_cnt`) CIF가 더미 버퍼에 쓴 뒤** 버퍼가 다시 들어올 때 호출됨(`capture.c` 함수 정의 4433행·호출 4714행, `lack_buf_cnt` 증가 1982·2010·2177행 등)
- (확실, 조회) 10fps 상태의 `/proc/rkcif-mipi-lvds`: 입력 모드 3864×2192@20, `csi over flow 0`, `csi bandwidth lack 0`, `not active buf cnt 0`, 프레임 종료 횟수가 전체 IRQ 횟수와 같음, **`total buf_cnt: 2`**(드라이버 안 1개). ISP 쪽 `frameloss:3`, 메인 출력 `frameloss:0`
- (확실, 소스) rkipc가 CIF raw 버퍼 수를 2개로 고정함: `common/isp/rv1106/isp.c` 104·170행 `rk_aiq_uapi2_sysctl_preInit_devBufCnt(sensor, "rkraw_rx", 2)`. 보드 원본·버퍼 3개 빌드 모두 같음. SDK 예제(`simple_vi_bind_venc_rtsp_three_camera_rv1106.c`)도 2
- (추측, 시험 안 함) 시작 직후 입력이 약 20fps로 들어오는 부팅에서 CIF 버퍼가 한 번 모자라 핑퐁 동기가 어긋나고 이후 프레임이 정확히 하나 걸러져 10.0fps가 유지되는 것으로 보임. 18fps로 시작하는 부팅은 이 상태를 피함. **왜 부팅마다 시작 fps가 18과 20으로 갈리는지는 모름** (센서 레지스터 VMAX 2250·HMAX 1650으로는 두 경우가 구분되지 않았음)
- 표본이 6회뿐이고 4회는 메시지·레지스터까지 확인, 2회는 fps만 확인했음. 상관일 뿐 인과는 입증하지 못함

**6. 해결 후보 (정리만, 적용하지 않음)**
1. **CIF raw 버퍼 수를 2 → 3으로**: `isp.c`의 `preInit_devBufCnt(..., "rkraw_rx", 2)` 두 곳을 3으로 바꾼 rkipc 빌드로 같은 재부팅 시험(6회 이상) 후 10fps 하락 비율 비교. 메인 VI 버퍼 3개 패치와 같은 계열이며 `patches/`에 패치 파일로만 남기고 보드는 시험 실행(`/tmp`)으로 확인. 메모리 비용: raw 프레임(3840×2160 10bit 약 10MB)이 1개 늘어남 — 보드 MemAvailable 약 109MB 안에서 확인 필요
2. **시작 직후 fps가 18인지 20인지의 원인 찾기**: 두 경우에서 센서 PLL·exposure·AE 시작값을 부팅 직후(업타임 12초부터) 비교. 이 원인을 알면 하락 자체를 피할 수 있을 수 있음
3. **시계 점프를 직접 시험**(승인 필요, 지금은 하지 않음): 18fps로 안정된 부팅에서 `date -s`로 시각을 앞으로 보내고 fps가 변하는지 확인. rkaiq의 `gettimeofday` 기반 대기가 실제로 영향을 주는지 판정. 콜드 부팅(전원 제거) 시험도 같이
4. **감시 + 재부팅**: 하락(10fps 지속)을 감지해 재부팅하는 방법. 정지 감시와 같은 도구에 넣을 수 있으나 "정지 감시는 아직 넣지 않음" 결정이 있으므로 보류

**현재 보드 상태**: 4회차 재부팅이 10fps 상태로 끝났고 그대로 둠(재부팅하면 18 또는 20으로 시작).

### 입력 10fps 하락 대응 — CIF raw 버퍼 3개, fps 18 시험 (2026-11-11 14:00~14:50, 사용자 승인)

가설(사용자): CIF raw 버퍼가 2개라 unite 모드에서 여유가 거의 없고, 입력이 20fps 근처면 한 번의 지연으로 pingpong(더미 버퍼 기록) 상태에 빠져 10fps로 고정된다. 18fps에서는 여유가 있어 유지된다. 파이프라인 정지도 같은 원인일 수 있다. 시계 가설은 기각

**1. 사전 확인 (조회만)**
- CMA(확실): `rk_dma_heap_cma=100M`. `CmaTotal` 102400 kB, `CmaAllocated` 62236 kB, `CmaReleased`(전체−사용) 40164 kB = **39.2 MiB 미할당**. `CmaFree` 0은 미할당 영역을 이동 가능한 페이지(페이지 캐시 등)가 쓰고 있다는 뜻(커널 `fs/proc/meminfo.c`). MPI(valloc) 버퍼 34개 합계 25.8 MiB, 나머지는 raw 버퍼·ISP 내부 버퍼
- raw 버퍼 1개: 3864×2192 10bit 패킹 = 10,587,360 B(10.10 MiB), 줄 길이 256바이트 정렬 시 10.17 MiB. 출력 crop 3840×2160 기준이면 9.89 MiB
- 판단: 1개 늘려도 미할당 약 29 MiB가 남아 **충분**. 시험 중 실측 `CmaAllocated`가 62236 → 72496 kB(+10.0 MiB)로 계산과 일치, MemAvailable 약 110 MB 그대로
- rkcif pingpong 복귀 경로(소스, `drivers/media/platform/rockchip/cif/capture.c`):
  - 프레임 끝(`rkcif_assign_new_buffer_update`, 2593행~): 대기 버퍼가 없으면 두 슬롯(curr/next)이 같은 버퍼를 가리키게 하고 `lack_buf_cnt`를 올림. 대기 버퍼가 있으면 다음 슬롯에 정상 할당
  - 버퍼 반환 시(`rkcif_buf_queue` → `rkcif_check_buffer_update_pingpong`, 4433행·호출 4714행): `lack_buf_cnt`>0이고 슬롯이 겹치거나 비어 있으면 빈 슬롯에 새 버퍼 주소를 바로 써서 복귀. 두 슬롯이 이미 서로 다른 버퍼면 아무것도 안 하고 4606행 메시지만 출력(우리가 본 메시지)
  - 더미 버퍼는 `is_use_dummybuf`(sysfs, 기본 꺼짐)일 때만 만들어짐. **강제 재동기화·스트림 재시작 같은 복귀 경로는 없음** → 사용자 공간(rkaiq)이 다음 프레임 끝 전에 버퍼를 돌려줘야만 원래 fps로 돌아옴. 반환이 매번 반 박자 늦는 상태가 자리 잡으면 10fps가 유지될 수 있음(소스로부터의 추론)

**2. CIF raw 버퍼 3개 빌드 (메인 VI 버퍼 3개 + raw 버퍼 3개)**
- 빌드: `~/rkipc-work/src-raw3`(src-buf3 복사본)에서 `common/isp/rv1106/isp.c`의 `rk_aiq_uapi2_sysctl_preInit_devBufCnt(..., "rkraw_rx", 2)` 두 곳을 3으로. 104행이 실제 경로, 170~171행(camgroup)은 이 빌드 설정에서 컴파일되지 않아 바이너리 동일. strip 후 461648바이트, md5 `8cfcb468…`. 경고 수는 기존 빌드와 같음(18줄)

### RKMPI 가이드 근거 — 메인 VI 버퍼 수 (2026-11-11)

근거 문서: `~/luckfox-pico/media/rockit/rockit/mpi/doc/Rockchip_Developer_Guide_MPI.pdf` V1.4.44(2023.03), 7.9 `VI_CHN_ATTR_S`의 【注意事项】 (PDF 111쪽). 로컬 변환본은 `docs/vendor/`(git 미추적)에서 `u32Depth的设置参考如下`로 검색

가이드 원문 요지: VI 뒤에 다른 모듈이 bind되어 있고 `RK_MPI_VI_GetChnFrame`으로 영상을 가져올 때는 `u32Depth`를 `VI_ISP_OPT_S.u32BufCount`보다 **최소 2 작게** 설정한다(예: `u32BufCount` 3, `u32Depth` 1). 너무 크면 정상 출력에 영향을 주거나 뒤 단계 프레임레이트가 부족해진다. `GetChnFrame`이 필요 없으면 `u32Depth`는 0을 권장

**확실 (소스와 가이드를 직접 대조)**
- 보드 원본 rkipc 메인 VI0: `u32BufCount` 2, `u32Depth` 1 (`video.c` 720·737행). 차이가 1이라 가이드의 "차이 2 이상" 권장을 만족하지 않음
- 버퍼 3개 빌드: `u32BufCount` 3, `u32Depth` 1 → 가이드 예시와 같은 값

**확인 필요였던 것 — rkipc 메인 VI0에서 `GetChnFrame`을 부르는 곳이 있는가 (소스 조사 결과, 확실)**
- `VIDEO_PIPE_0`(메인 VI0)을 대상으로 한 `RK_MPI_VI_GetChnFrame` 호출은 `rkipc_get_vi_send_jpeg`(`video.c` 234행) **한 곳뿐**. 이 스레드는 `rkipc_pipe_jpeg_init()`(1745행)에서만 만들어지고, 그 함수는 `enable_jpeg`일 때만 호출됨(3371행). 보드 ini의 `video.source:enable_jpeg = 0`이므로 **현재 설정에서는 호출되지 않음**
- 나머지 `GetChnFrame`은 다른 파이프용: 83행(`VIDEO_PIPE_1`, `get_vi_send_vo`는 `HAS_VO 0`이라 컴파일 안 됨, 바이너리에 VO 심볼 없음 확인), 333행(`VIDEO_PIPE_1`, 스레드 생성이 1439행에서 주석 처리), 548행(`VIDEO_PIPE_2`, IVS용)
- 메인 VI0의 실제 소비자는 `RK_MPI_SYS_Bind`로 연결된 VENC0(`video.c` 1060~1068행) 하나. IVS는 VI 파이프 2에 bind(1659행)되어 VI0과 무관
- `common/`과 `rv1106_ipc/` 소스에서 `GetChnFrame` 호출은 `video.c`뿐. 다만 `librockit` 내부 동작은 소스가 없어 확인 불가

**해석 (추측, 구분해서 읽을 것)**
- 가이드의 조건("GetChnFrame 사용 시 차이 2 이상")은 **현재 설정의 메인 VI0에는 그대로 해당하지 않는다.** 따라서 이 가이드를 "원본 2/1이 문제였다"는 직접 증거로 쓸 수는 없음
- 가이드는 "bind만 쓰고 GetChnFrame이 필요 없으면 `u32Depth`는 0"을 권장하는데, rkipc는 메인 VI0에 `u32Depth = 1`을 줌. 가이드 문구상 depth가 높으면 후단 fps가 부족해질 수 있으므로, **버퍼 2·depth 0이면 버퍼 3개 없이도 해결되는지**는 시험하지 않았음(확인 필요, 다음 후보)
- 지금까지의 근거는 시험 결과(버퍼 2: 메인 손실 약 50%, 버퍼 3: 손실 0%·약 18fps, 14시간 정지 0회)이며 가이드는 보조 설명임
