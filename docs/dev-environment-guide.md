# SmarcleSafe 개발 환경 정보 제공 가이드

> **참고:** 이 문서는 자동으로 로드되지 않음. `CLAUDE.md`에 이 문서로 가는 참조가 있으므로, 필요할 때 해당 섹션을 직접 읽을 것.

## 이 문서의 목적

Claude Code에게 매 세션마다 개발 환경(SDK, 저장소, 보드)을 처음부터 다시 설명하지 않기 위한 가이드임. 개발 환경을 아래 세 레이어로 나눠서, 레이어별로 "무엇을 기록해둬야 하는지" / "무엇을 캐싱해서 재탐색을 피할지"를 정리함.

이 문서 자체는 체크리스트이지 실제 값이 채워진 데이터가 아님. 실제 값(SDK 경로 스캔 결과, 보드 스냅샷 등)은 이 문서가 지정하는 별도 파일에 채워 넣는 것을 전제로 함.

## 참고: 현재 개발 환경 토폴로지

- 보드: LuckFox Pico Zero (SoC: RV1106)
- 보드 ↔ Windows PC: USB 연결, `adb`로 통신
- PC 개발환경: Windows 위 VMware Ubuntu 게스트 → 그 안에서 VSCode + LuckFox 공식 SDK(Buildroot 기반)
- USB는 VMware가 우분투 게스트로 패스스루 → `adb` 명령은 게스트 우분투 안에서 실행

> ✅ 확정됨(2026-09-18): 개발 보드는 **LuckFox Pico Zero (RV1106)** 로 픽스됨. 이전에 남아있던 Pico Plus(RV1103) 표기는 정리 완료.
>
> 서버 레이어(이 문서의 범위 밖): 클라우드 브리지 서버는 **Node.js(Express), AWS** 사용 (서버 코드는 이 저장소에 없음). ARIA-256-GCM은 커널에 `CONFIG_CRYPTO_ARIA`가 없어서 유저스페이스에서 구현하는 걸로 설계 확정 — 착수 여부 같은 진행 상황은 이 문서에 담지 않음(`CLAUDE.md` 설계 원칙과 동일).

## 레이어 1 — SDK (vendor tree, 로컬 경로: `~/luckfox-pico`)

### 왜 별도로 캐싱해야 하는가

Buildroot 기반 SDK는 커널/툴체인/미디어 스택까지 포함돼 파일 수가 매우 많음. 매 세션 `tree`나 `find`로 전체를 다시 훑으면 시간과 토큰 낭비가 큼 → 한 번 확인한 정보는 캐시 파일에 박아두고, SDK가 바뀔 때만 갱신.

### 체크리스트 — 기록해둬야 할 정보

1. **툴체인**
   - 절대 경로 (예: `~/luckfox-pico/tools/linux/toolchain/...`)
   - prefix 정확한 문자열 (예: `arm-rockchip830-linux-uclibcgnueabihf-`)
   - `gcc --version`, `g++ --version` 출력
2. **sysroot / 헤더·라이브러리 위치**
   - sysroot 경로
   - 주요 헤더 디렉토리 위치 (RKMPI, RKNN, RGA, VENC/MPP 등 미디어 스택 헤더가 어디 있는지)
   - `.so` / `.a` 라이브러리 경로, static/dynamic 링크 여부 확인 결과
3. **커널**
   - 커널 소스 경로, 버전, defconfig 이름
   - 이미 확인한 config 옵션 (예: `CONFIG_CRYPTO_ARIA` 미포함 확인 방법 — `grep ARIA .config` 등)
   - 디바이스트리 소스 경로
4. **Buildroot 산출물**
   - 최종 이미지 출력 경로 (boot.img, rootfs.img 등)
   - rootfs 재빌드 명령어
5. **레퍼런스 앱 구조**
   - SDK 내 예제 앱 경로 (예: `project/app/rkipc/rkipc/`)
   - 각 예제가 참조하는 라이브러리 목록, 공통 로직과 타겟별 로직이 어떻게 나뉘는지
   - SDK에 내장된 1차 문서 위치 (예: rkipc 공식 개발자 가이드가 소스 트리 안에 포함돼 있는 경우 — 웹 검색보다 이게 정확할 가능성이 높음)
6. **SDK 메타 정보**
   - SDK 버전/브랜치/커밋 해시, 확인 날짜
   - 공식 저장소/Wiki 링크

### 캐싱 전략 (매번 전체 재스캔 방지)

- 위 내용을 리포 안의 한 파일로 유지 (예: `docs/sdk-reference.md`). Claude 프로젝트 쪽에 이미 유사한 탐색 기록(`sdk-directory-exploration.md`)이 있다면, 그 내용을 이 리포의 캐시 파일로 옮기거나 링크로 연결해서 이중 관리를 피할 것.
- 캐시 파일에는 반드시 **"확인 날짜"** 와 **"SDK 커밋/버전"** 을 같이 기록 — SDK가 업데이트되면 이 값이 캐시 무효화 신호가 됨.
- 탐색은 "관심 디렉토리를 얕게 훑기 → 필요한 디렉토리만 깊이 제한 없이 다시 파기"의 2단계로 진행하는 게 효율적 (SDK 트리가 넓고 깊어서 한 번에 전체를 깊이 보면 노이즈가 큼).
- 새로운 SDK 영역(예: NPU/RKNN 관련 디렉토리)을 처음 볼 때만 이 캐시 파일을 갱신 — 이미 기록된 영역은 재탐색하지 않는 게 원칙.

## 레이어 2 — 유저스페이스 프로젝트 (이 저장소, `~/BoardServer`)

이건 워크스페이스 자체이므로 Claude Code가 매 세션 직접 열람 가능 — "여기에 뭐가 있다"를 별도로 문서화할 필요는 크지 않음.

### 예외적으로 기록해두면 좋은 것

- 저장소 밖(SDK 등)을 참조하는 절대 경로 (예: 빌드 스크립트에서 `~/luckfox-pico`를 하드코딩 참조하는 부분)
- `.gitignore`로 안 보이지만 실제로 존재하는 로컬 전용 설정/스크립트
- **"정리 중" 상태**: 예를 들어 `pcap_test.c` 등 libpcap 실습 코드를 `experiments/`로 옮겼던 것처럼, 최종 위치가 아직 아닌 파일들의 이동 계획. 이런 건 이 문서나 `CLAUDE.md`에 "현재 진행 중" 한 줄로 남기는 정도면 충분하고, 완료되면 그 줄을 지우면 됨.
- 저장소 최상위 구조가 목적과 다르게 보이는 예외 (예: 특정 디렉토리가 이름과 다른 역할을 하는 경우)

## 레이어 3 — 보드 런타임 상태 (물리적으로 분리된 디바이스, USB/adb로만 접근)

**업데이트(2026-09-17): Claude Code CLI가 VMware Ubuntu 게스트 셸에서 실행되고 adb도 그 셸에서 동작하는 게 확인됨** → Claude Code가 `adb shell "<명령>"`으로 보드에 직접 접근 가능함 (root 권한). 아래 항목들을 사용자가 손으로 확인해서 붙여넣을 필요 없이, Claude Code가 스스로 조회해서 스냅샷 파일에 기록할 수 있음. (이 레이어 설명이 원래 "Claude Code가 직접 접근 불가"였는데, 실제 환경에서 확인해보니 아니었음 — 이 문서는 초안 단계에서 작성된 거라 이 문구만 예전 가정임.)

### 스냅샷에 남겨야 할 항목

- **부팅 서비스**: `adb shell ls -la /etc/init.d/` — 어떤 서비스가 부팅 시 자동 실행되는지
- **WireGuard 상태**: `adb shell wg show`, `adb shell ip addr show wg0`(또는 실제 인터페이스명) — 터널이 살아있는지, 어떤 피어가 연결됐는지
- **마운트 상태**: `adb shell mount`, `adb shell df -h` — rootfs가 read-only인지 overlay인지, eMMC 파티션 사용량
- **커널/라이브러리 버전**: `adb shell uname -a`, 주요 `.so` 버전 (`adb shell ls -la /usr/lib/*.so*` 등)
- **네트워크 인터페이스**: `adb shell ip addr`, `adb shell ip route`
- **핵심 프로세스 상태**: `adb shell ps` — 보드 서버 프로세스, WireGuard, rkipc 등 떠 있어야 할 것들이 실제로 떠 있는지
- **로드된 커널 모듈**: `adb shell lsmod` — 단, 센서 드라이버처럼 커널 빌트인이라 `lsmod`에 안 뜨는 것도 있으니 "안 뜬다 = 안 로드됐다"로 단정하지 말 것
- **adb 연결 방식**: USB 시리얼 기반인지, 네트워크 adb인지 (지금 토폴로지 기준으로는 USB 패스스루 경유)

### 기록 형식/파일

- 저장 위치 제안: `docs/board-snapshot.md` (이 가이드와 같은 위치)
- 형식: 날짜/시각 헤더 + 각 명령어와 **원본 출력을 가공 없이** 코드블록으로 붙여넣기 (나중에 스냅샷 간 diff로 "무엇이 바뀌었는지" 비교하는 게 목적이므로 요약하지 말 것)
- 예시 템플릿:

  ````
  ## 2026-09-17 15:30 KST

  ### /etc/init.d/
  $ adb shell ls -la /etc/init.d/
  <원본 출력>

  ### wg show
  $ adb shell wg show
  <원본 출력>
  ````

- 오래된 스냅샷에는 날짜를 남기고, 새 스냅샷은 이전 항목 위에 누적(최신이 위)하거나 별도 섹션으로 구분 — 과거 상태와 비교할 수 있게 유지.

### 갱신 빈도

- **원칙**: 보드 상태를 바꾸는 작업(서비스 추가/삭제, WireGuard 설정 변경, 커널 모듈 로드/언로드, 마운트 구성 변경) 직후마다 갱신
- **최소 주기**: 보드 관련 작업을 하는 세션이라면 세션 시작 시 한 번, 세션 중 상태가 바뀌었다면 종료 전에 한 번 더
- 스냅샷이 오래됐다면(예: 마지막 기록이 며칠 전) Claude Code에게 "이 스냅샷은 오래됐으니 현재 상태로 가정하지 말라"고 명시할 것 — 오래된 스냅샷을 현재 상태로 착각하는 게 가장 흔한 실수 원인.

## 작업 방식 규칙 (Claude Code가 지켜야 할 것)

1. SRS 요구사항 ID 하나씩만 작업 — 여러 ID를 한 번에 묶어서 진행하지 않음
2. 코드를 통째로 던지지 않음 — **개념 → 원리 → 코드 조각** 순서로 진행
3. 확실한 사실과 추측을 명확히 구분해서 말하기 ("~인 것 같습니다"로 얼버무리지 않기)
4. 명령어 제시 시 한국어 인라인 주석으로 옵션/키워드 의미 설명
